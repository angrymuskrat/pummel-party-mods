# Тематический пак: доска + мини-игры под одну тему

Цель проекта — несколько тематических карт (досок) и под каждую свой набор мини-игр. Этот скилл ведёт от темы до спецификаций, которые человек собирает мышкой в Mod Editor. Он не описывает редактор — для этого `pummel-party-mod-editor` и его `reference/`.

## Структура пака в репозитории

```
packs/<theme-slug>/
  PACK.md                 # тема, тон, палитра, список мини-игр со статусами
  board/
    BOARD.md              # схема доски, кастомные клетки, событийные цепочки
  minigames/<game-slug>/
    DESIGN.md             # спецификация по шаблону ниже
  assets/
    models/  textures/  audio/   # исходники и скрипты генерации (Blender/Python/PIL)
    ASSETS.md             # что нужно, что готово, кто делает
```

Каждый мод в редакторе — либо доска, либо мини-игра, и тип не меняется. Пак — это одна доска + N мини-игр, опубликованных отдельными Workshop-предметами с общей темой в названии.

## Процесс

1. **Тема.** Записать в `PACK.md`: сеттинг в двух предложениях, 3–5 визуальных якорей, тон (мультяшный / мрачный / абсурд), что игроки должны чувствовать. Если темы нет — брейншторм через `grilling` (вопросы раундами с рекомендованным ответом).
2. **Доска.** Схема: сколько клеток, развилки, где кастомные клетки, какое событие на каждой. Для каждой кастомной клетки — цепочка «событие → действия» из каталога. Если механика требует действия, которого в каталоге нет, — пометить «не реализуемо в редакторе» и предложить замену из существующих действий.
3. **Набор мини-игр.** 4–6 на пак, разных по типу (гонка, выживание, сбор, дуэль, кооп против среды). На каждую — одна строка идеи в `PACK.md`, затем отдельный `DESIGN.md`.
4. **Спецификация мини-игры** — шаблон:
   - Цель и условие победы одной фразой.
   - Длительность, число игроков, нужен ли таймер.
   - Сцена: список гейм-объектов с компонентами (имена компонентов как в вики).
   - Логика: таблица `Событие | Действия по порядку | Параметры`. Только имена из `logic-catalog.md`.
   - Ассеты: модели (.obj), текстуры, звуки — с пометкой «генерировать кодом» или «ручная работа».
   - Риски: что может не синхронизироваться, что непонятно по вики.
5. **Ассеты кодом.** Процедурные .obj через Python или Blender-скрипт, текстуры через PIL, звук синтезом. Скрипты лежат рядом с результатом в `assets/`, чтобы ассет можно было перегенерировать.
6. **Проверка в редакторе** — делает пользователь. Я готовлю чеклист: что нажать в плейтесте, что должно произойти, какие ошибки Mod Validator ожидаемы. Скриншоты Log Window и Validator разбираю по запросу.

## Что умеет и не умеет логика редактора (по `logic-catalog.md`)

- Нет переменных, условий if/else, счётчиков, циклов. Логика = событие → линейный список действий сверху вниз; паузу дают только `Wait Action` и `Display Popup` (доска).
- Единственное «состояние»: очки и здоровье игрока (Set/Add/Subtract/Multiply/Divide), `Set Active` на объектах (событие `Enable` у `Logic Component` работает как сигнал), флаги триггера `One Use Per Player` / `Disable After Triggered`, случайный выбор (диапазон `Wait`, таймер между двумя значениями, случайный префаб/предмет/клетка).
- Победа только через End Conditions мода: `Timer`, `ObtainPoints`, `RemainingPlayersAlive`, `FinishMinigame` + Placement Condition.
- Любую механику со «если игрок X, то…» переформулировать через эти кирпичики или честно пометить «не реализуемо».

## Правила

- Проектировать только из того, что есть в `reference/logic-catalog.md`; если каталог молчит — сказать «по вики не подтверждено» и не выдумывать параметры.
- Одна мини-игра — один `DESIGN.md`; не смешивать несколько игр в одном файле.
- Сборка сцены мышкой — за пользователем; через computer use это слишком медленно, не предлагать без запроса.
- Публикация в Workshop, запуск игры и Steam-действия — по запросу пользователя.
